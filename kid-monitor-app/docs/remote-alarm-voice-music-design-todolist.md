# 监控端远程闹钟「语音 + 音乐」设计与 ToDo List

## 目标

家长在家长端编辑闹钟标题和提醒内容后，目标监控 Pad 在到点时播放**循环背景音乐**与**腾讯云合成的提醒语音**。语音播报期间音乐自动降低音量，播报完毕恢复；关闭闹钟时音乐、语音、振动、通知和前台服务一并结束。

该能力是既有远程闹钟的音频增强，不改变其可靠性边界：到点触发仍由已经落地到 Pad 的 `AlarmManager.setAlarmClock` 执行，不能将“闹钟响铃时在线请求 TTS”作为正式路径。

## 现状与结论

- 家长端已提供标题和“提醒内容（可选）”编辑，并通过 `alarms.title`、`alarms.message` 同步到目标 Pad。
- 监控端已将标题和内容保存到 `device_alarms`，并在 `AlarmRingService` 中取得 `USAGE_ALARM` 音频焦点、振动、保活和播放系统默认闹钟铃声。
- 项目已有腾讯云短文本 TTS 事件函数 `generate-literacy-audio`，使用 `TextToVoice` 生成 MP3；其现有资产表、对象路径、清理逻辑和每日额度均面向认字教学，**不得直接复用为闹钟资产**。

因此，采用“云端预生成提醒人声 + Pad 本地缓存 + Pad 双播放器混音”的方案。音乐作为 App 内置、可离线循环的资源；腾讯 TTS 只负责可变的文字人声。这样既可固定音色，也能保证闹钟触发时网络中断不影响播放。

## 范围与非目标

### 本期范围

1. 家长可输入闹钟标题和提醒内容，并选择一首内置背景音乐。
2. 保存或编辑闹钟后，为该 revision 异步生成腾讯 TTS MP3。
3. Pad 同步闹钟时下载并校验对应 MP3，缓存在应用私有目录。
4. 到点循环播放背景音乐，并按设定间隔播放“标题 + 提醒内容”语音；语音期间自动压低音乐。
5. 任一音频资源不可用时均有可审计的降级路径，且不影响精确闹钟、全屏通知和关闭回执。

### 非目标

- 不允许家长上传任意音乐文件，也不在本期提供在线音乐库，避免版权、审核、下载和离线缓存问题。
- 不在腾讯云将音乐和语音预混成单个 MP3：这样每次编辑文字都要重新混音，且会失去本地调节音乐音量、循环和降级能力。
- 不向 Android 客户端发放腾讯云长期密钥，也不让客户端直接调用腾讯 TTS。
- 不承诺所有 Android 设备的系统本地 TTS 音色一致；本地 TTS 只作为腾讯语音缓存不可用时的兜底。

## 用户体验与播报规则

### 家长端编辑

闹钟编辑弹窗保留现有“标题”和“提醒内容”，并增加：

| 配置 | 规则 |
| --- | --- |
| 背景音乐 | 必选，首期提供少量随 App 内置的曲目；默认一首温和的闹钟音乐。 |
| 语音播报 | 默认开启；关闭时只播放背景音乐和振动。 |
| 播报文本 | 按 `标题 + 提醒内容` 组装。提醒内容为空时只朗读标题。去首尾空白后限制在腾讯接口和产品共同约定的长度内。 |
| 重复间隔 | 首期固定为 20 秒；从一次语音播放完成开始计时。后续可开放 15 / 20 / 30 秒选项。 |

保存中应明确显示“正在保存闹钟”；闹钟写库成功和腾讯音频生成成功是两个独立状态。家长端可展示“已下发，语音准备中 / 语音已缓存到 Pad / 已使用离线降级”，但不能把“语音尚未就绪”误报成“闹钟未部署”。

### Pad 到点播放

```text
AlarmManager 触发
  -> AlarmReceiver
  -> AlarmRingService（取得一次 alarm 音频焦点、唤醒锁、振动、全屏通知）
       -> AlarmAudioController
            -> 背景音乐：内置资源循环播放，正常音量 100%
            -> 提醒语音：优先播放本地校验通过的腾讯 MP3
                 开始：背景音乐淡出/压低至 25%
                 完成：背景音乐恢复至 100%，等待 20 秒
                 下一轮：重复提醒语音
```

- 首次语音应在背景音乐启动后尽快播放，不等待第一个 20 秒间隔。
- 多次语音不会叠加；上一轮未结束时不启动下一轮。
- 用户点击关闭、服务自动超时、闹钟被取消或服务销毁时，必须取消等待任务，停止并释放两个播放器。
- 同一时刻的多闹钟仍遵守既有并发策略；本方案不能使不同闹钟的背景音乐和语音互相叠加。

## 数据模型与版本规则

### 云端 `alarms`

在现有表中新增与本功能直接相关的配置和生成状态字段（名称以最终迁移为准）：

| 字段 | 示例 / 约束 | 用途 |
| --- | --- | --- |
| `background_music_id` | `gentle_bell_v1`，非空 | 映射 Pad 内置音乐资源；只接受白名单值。 |
| `voice_enabled` | `true` | 是否播报人声。 |
| `voice_text` | 规范化后的标题 + 提醒内容 | 生成时的不可变输入，便于审计和判断是否需要重生成。 |
| `voice_status` | `pending` / `processing` / `ready` / `failed` | 云端语音资产状态。 |
| `voice_audio_url` | 仅 `ready` 时非空 | 供已认证目标 Pad 下载的音频地址或受控对象标识。 |
| `voice_audio_sha256` | 64 位摘要 | Pad 下载后校验内容，避免损坏缓存被当作有效音频。 |
| `voice_version` | 如 `alarm-v1` | 音色、语速或合成参数变更时用于缓存失效。 |

文本、背景音乐、语音开关或合成参数改变都必须递增 `alarms.revision`，确保 Pad 不会继续播放旧内容。`voice_status` 从 `pending` 变为 `ready` 时可更新音频字段，但不得改变闹钟的触发语义，也不得让旧版本回执覆盖新 revision。

### Pad `device_alarms`

将必要的音频描述与当前缓存状态持久化在 Room：`backgroundMusicId`、`voiceEnabled`、`voiceText`、`voiceAudioUrl`、`voiceAudioSha256`、`voiceVersion`、`voiceCacheState`。缓存文件使用由 `alarmId + revision + voiceVersion` 派生的私有文件名，不能直接以家长文字作为路径。

缓存状态建议为 `not_required`、`pending_download`、`ready`、`failed`。它是设备侧诊断状态，不取代现有 `alarm_deliveries.status`：

- `deployed`：精确闹钟已成功登记，保持现有含义。
- `voice_ready`：作为新增的、可选的音频就绪信息或事件详情上报，供家长端展示。
- 语音下载失败不能撤销已登记的闹钟；到点进入本地 TTS 或系统铃声兜底。

## 云端合成与存储

新增独立的 `generate-alarm-audio` 事件函数，或在充分解耦后为现有生成函数增加独立的 `alarm` 资产域；本设计优先前者。无论采取哪种实现，必须满足：

1. 独立的 `alarm_tts_assets` 表、对象路径前缀、清理策略、每日字符额度和监控日志，不能与 `literacy_tts_assets` 交叉读取或清理。
2. 使用服务端保存的腾讯云凭证调用 `TextToVoice`，生成 MP3；密钥、完整对象 URL 和家长文本不得写进客户端日志或公共监控日志。
3. 保存闹钟后由可信服务端入队，而不是让家长 App 直接带 service role 创建资产。
4. 上传对象后校验 HTTP 响应、`audio/mpeg`、非零大小和 SHA-256；仅随后把资产置为 `ready`。
5. 删除闹钟、关闭语音、更新 revision 后，使旧资产进入可重试的延迟清理队列。Pad 已缓存的旧文件也应在同步到新 revision 后删除。
6. 音频对象采用受认证下载或短时签名 URL；不能因闹钟音频而将家庭提醒文本暴露到公共 bucket。

函数可以沿用项目现有腾讯 TTS 的音色参数（当前认字端为爱小芊 MP3），但应为闹钟单独设定 `TENCENT_ALARM_TTS_*` 环境变量和版本号，避免教学音色调整意外影响闹钟。

## Pad 音频实现

### `AlarmAudioController`

从 `AlarmRingService` 抽出单一音频协调器，持有一个共享的 `AudioManager` 焦点和两个独立播放器：

| 播放器 | 数据源 | 属性与行为 |
| --- | --- | --- |
| `backgroundPlayer` | `res/raw` 内置音乐 | `USAGE_ALARM`、`CONTENT_TYPE_MUSIC`，循环；音量可动态调节。 |
| `voicePlayer` | 本地腾讯 MP3 缓存 | `USAGE_ALARM`、`CONTENT_TYPE_SPEECH`，单次播放；完成回调触发恢复音乐和下一轮计时。 |

首期可继续使用平台 `MediaPlayer`，不必为这项能力引入新的播放框架；重点是封装准备、播放、停止、错误处理和释放，避免 `AlarmRingService` 中出现相互竞争的播放器回调。

音频焦点只申请一次，两个播放器共用；不要分别申请焦点，否则语音开始时会中断自己的背景音乐。遇到永久音频焦点丢失时应停止播放并记录原因，遇到短暂丢失可暂停后尝试恢复，始终保留全屏通知和关闭入口。

### 离线与失败降级

优先级如下：

1. 已校验的腾讯语音缓存 + 内置背景音乐（目标效果）。
2. 内置背景音乐 + Android 系统 TTS 朗读 `voiceText`。
3. 内置背景音乐；若音乐资源也初始化失败，播放当前系统闹钟铃声。

无论哪一层失败，都继续振动、维持前台服务/唤醒锁、发送全屏通知并可关闭；不得出现“因为语音失败所以整个闹钟不响”。首次下载和更新下载仅可在正常同步期间进行，不应在 `AlarmReceiver` 的到点冷启动路径中等待网络。

## 同步、回执与安全

1. 家长保存闹钟，数据库原子更新闹钟 revision 和投递记录，并入队语音资产。
2. Pad 同步到 `pending` 资产时先登记精确闹钟，同时把语音标为待下载；不阻塞部署回执。
3. 资产变为 `ready` 后，Pad 下一次轮询、启动、解锁或未来的 Realtime 加速同步获取 URL，下载、摘要校验并原子替换缓存文件。
4. Pad 写入音频就绪/失败诊断事件；家长端基于最后一次状态提示，而不是假设每台 Pad 都已缓存。
5. 到点只从 Room 和本地缓存读取，网络不可用不影响响铃。

RLS 必须限制父母只能管理本家庭闹钟，监控 Pad 只能读取与自身 `device_id` 匹配的音频元数据。任何需要 service role 的入队、合成、回写、签名和清理操作都仅在云函数内执行。
