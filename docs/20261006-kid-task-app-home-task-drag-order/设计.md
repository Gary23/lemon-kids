# 设计：今日任务卡拖动排序

## 问题分析

`HomeViewModel` 读取 `TaskRepository.observeChildTasks()` 后，先按状态对今天的任务排序；`buildHomeTaskLayout()` 再把未完成任务按家长配置的分类顺序排序。`HomeDashboard` 将任务分成左侧“待完成任务”和右侧“今天已完成”两列，目前用普通 `Column` 逐张渲染。即使只在界面交换卡片，下一次观察流刷新、页面重建或应用重启仍会恢复默认顺序。`tasks` 数据表没有首页专用顺序字段，家长端和桌面小部件也消费任务数据。

## 方案目标与范围

- 首页左侧“待完成任务”卡片使用整卡长按拖动，无独立把手与占宽留白。长按后卡片抬起、黄色描边、轻微摆动并触发一次触感反馈；手指移动时卡片跟手，邻卡让位，松手确定顺序。短按朗读、打卡仍由原控件处理。
- 待完成列表可跨分类任意重排；分类仍显示在卡片标签中，不再强制把手动排序的任务按分类排回去。右侧“今天已完成”列表不提供拖动，继续沿用当前展示顺序；任务状态仍决定所属列表，不能通过拖动移列。
- 顺序只影响本机当前孩子账号的今日任务首页。日期、账号之间隔离；不改变家长端、日历、未来计划、桌面小部件及服务端任务数据。

## 数据与交互流程

1. 以 `childId + yyyy-MM-dd` 作为本地排序键，仅保存待完成任务的有序 ID 数组 `pendingIds`。`DONE`、`VERIFIED` 属于已完成列，其余今日可见状态属于待完成列。只存 ID，不复制任务详情或状态。使用 `kid-task-app` 私有 `SharedPreferences` 保存版本化 JSON 记录。
2. 首页获取当前登录孩子与当日任务后，先读取对应本地顺序，再展示列表，避免先显示默认顺序又跳到保存顺序。没有保存记录时沿用当前状态及分类默认顺序。旧版本无需迁移；本地记录格式包含版本号，格式错误时回退默认顺序。
3. 将本地顺序与最新服务端任务快照合并：只保留当前日期仍存在且仍待完成的 ID，按已保存次序展示；尚未记录的新待完成任务在列表末尾依现有默认顺序追加。已取消任务自然消失。打卡后任务离开待完成列表，并按原有规则进入已完成列表；撤销后该任务进入待完成列表末尾。分类改名或分类配置变动不覆盖手动顺序。已完成列表仍按现有任务快照顺序展示，不读取本地排序记录。
4. 每轮拖动固定手势监听槽位并冻结实测卡片位置，只由该轮起始顺序、真实指针位移及实际滚动距离计算完整预览。长按静止只显示拿起反馈；真实移动达到小门槛后才允许换位和边缘滚动。基础布局在拖动及松手回位动画期间不变，邻卡只移向本轮目标槽位；回位后一次性提交顺序并销毁本轮动画状态。取消不保存。成功后维持显示；失败则恢复最近一次已保存顺序并提示“排序保存失败，请重试”。连续写入串行处理，后一次顺序不会被前一次写入覆盖。
5. 任务观察流重拉、从后台恢复或 App 重启都重新以对应键合并顺序。切换账号后先清掉旧账号的界面状态再加载新账号记录。跨日期后首页按当天重新取键和任务快照，不复用昨天列表。

## 接口与兼容性影响

不改 `:shared` 的 `Task` 或 `TaskRepository`，不改 Supabase 表和 RLS，也不增加网络写入。旧用户首装该版本仍按当前默认顺序显示；第一次拖动后才生成本地记录。同一孩子在另一设备上使用时保持该设备原有顺序。清除 App 数据或卸载后本地记录消失。

## 风险与回滚

- 整卡长按可能与短按、滚动手势竞争；长列表拖到可视区域边缘须继续滚动，松手/取消手势不能误触朗读或打卡。目标设备以横屏 Pad 验证。
- 任务状态与服务端刷新可能在拖动中变化；以最新任务快照为准，任务若已移列或删除，取消当前拖动并重新合并，避免保存失效 ID。
- 本地保存若失败，必须回退并提示；记录损坏时回到默认排序，不影响任务读取和打卡。回滚代码时任务数据不变，旧版忽略本地排序记录。

## 验收与验证

自动测试覆盖默认顺序、待完成排序、跨分类、重启读取、新增/删除、完成/撤销、已完成列表不受影响、账号/日期隔离及异常记录。执行 `./gradlew :kid-task-app:testDebugUnitTest :kid-task-app:assembleDebug`，通过后依流程请求安装确认，再在设备上实际拖动、完全退出重开、后台恢复、打卡/撤销及账号切换，等待用户确认人工测试结果。

## 待用户确认的设计决策

- 仅待完成列表可整卡长按拖动并跨分类排序；已完成列表不可拖动，继续沿用现有顺序。
- 顺序按孩子和日期保存在当前设备，退出重开有效；不做跨设备同步。
- 新待完成任务及撤销后回到待完成列表的任务追加到末尾；没有手动排序记录时沿用当前默认顺序。

## 补充与缺陷设计归并

### 整卡长按与视觉反馈

原版左侧 `38.dp` 把手挤占卡片宽度。用户在 Pad 测试后提出整卡长按，批准补充设计。移除把手和留白；长按标题、空白或操作区时，卡片抬起、放大约 1.04 倍、黄色描边并轻摆，触发一次触感反馈，标题旁给出“长按任务卡可调整顺序”提示。拖动过程中不触发朗读或打卡，短按仍执行原动作；系统关闭动画时保留静态位置及描边反馈。已完成列不绑定拖动手势。本地 `pendingIds` 格式不变。

### 缺陷根因与最终重构

Pad 崩溃堆栈显示 `Integer cannot be cast to InfiniteTransition`，首个应用帧在条件式 `rememberInfiniteTransition`。首轮移除该条件式记忆状态后，用户又发现相邻换位闪回、静止长按跳位、连续换位后邻卡不到位及第三条错误占位。中间几轮围绕阈值、窗口坐标和邻卡动画修复，仍存在基础列表顺序与旧动画状态交叉的问题。第五轮获用户明确批准，整体重写拖动链路：

1. `PendingTaskDragColumn` 为每次长按建立独立会话，冻结任务 ID 顺序、实测槽位、指针窗口坐标和滚动累计量；手势监听位于固定槽位，视觉动画仅作用在内部绘制层。会话编号隔离动画实例。
2. `HomeTaskDragLayout` 从同一份起始快照计算目标索引、完整预览顺序和每张卡片的目标偏移；未跨越的卡片保持零偏移。指针位移与页面实际滚动量分别累计一次，长按静止不会触发换位或边缘滚动。
3. 拖动和松手回位时保持基础列表原顺序；被拖卡片跟手，邻卡在松手前移到各自目标槽位。回位完成后提交 ViewModel 顺序并清理会话。取消或任务快照变化时丢弃预览；短按、已完成列表和本地保存规则继续沿用主设计。

第一轮至第五轮缺陷设计均在代码修改前获得用户明确“批准”；第五轮回复为“批准，完成后安装”，同时预先确认自动测试通过后安装 Pad。验证包含 JVM 几何与数据测试、Pad Compose 连续交换手势测试、Debug APK 构建和用户最终人工验收。仅修改 `kid-task-app`，共享接口、数据库及其他应用不受影响。
