# 需求：今日任务列表拖动排序并保存

- 需求编号/目录：`20261006-kid-task-app-home-task-drag-order`
- 日期：2026-10-06
- 应用范围：`kid-task-app`（柠檬任务）
- 提出人：用户
- 原始需求：“柠檬任务app，我需要在首页任务列表增加一个功能，任务顺序可以随意拖动，拖动后再次退出app后再打开要保持拖动后的结果，你来设计一下这个需求”
- 用户补充：“已完成列表不需要拖动，只需要拖动待完成列表”
- 人工测试期间的补充：“左侧的拖动区域占用了太多列表空间，我希望直接长按列表项就会出现一个孩子一看就是可以移动的动画效果，然后直接拖动，而不是单独有个拖动区域。”

## 背景与目标

首页今日任务当前按任务状态、家长配置的分类顺序显示，孩子无法调整卡片先后。目标是在首页直接拖动任务卡排序，并在退出、重新打开应用后恢复顺序。

## 范围与约束

- 仅调整当前孩子账号首页“待完成任务”列表的显示顺序，允许跨分类移动；“今天已完成”列表不可拖动，沿用现有展示规则。拖动不修改任务的分类、状态、日期、积分或家长端配置。
- 顺序按孩子账号和任务日期保存在本设备，重新打开本 App 后仍有效。不同孩子、不同日期互不影响。
- 保留现有打卡、撤销、朗读、进度与两列布局；任务状态变化仍决定其所属列。
- 不处理任务日历、未来计划、家长端、桌面小部件的排序同步；不提供跨设备同步和卸载/清除数据后的恢复。
- 遵守 `docs/README.md`：设计获明确批准后才能改功能代码，自动测试后取得安装确认，人工测试通过后才能完成及推送。

## 依赖与跨模块影响

任务 ID、日期、状态继续来自 `:shared` 的 `TaskRepository`；排序只在 `kid-task-app` 本地保存，不改共享模型、云函数或 Supabase 数据库。本流程仅覆盖 `kid-task-app`。

## 验收标准

1. 待完成任务卡无独立把手或预留区域；从卡片文字、空白及操作区域长按均可进入拖动，出现抬起、高亮、轻摆和触感反馈，再直接拖到列表内任意位置，包括不同分类之间。已完成任务卡不能拖动。
2. 完全退出并重新打开 App，当前孩子今天的待完成顺序保持；从后台恢复和任务数据刷新也不还原排序。
3. 打卡后任务按原有规则进入已完成列表；撤销后返回待完成列表末尾。新任务进入列表、任务被删除或修改分类后不会破坏已保存待完成任务的相对顺序；切换孩子账号及进入新日期不会串用旧顺序。
4. 朗读、打卡、撤销和页面滚动可正常使用；拖动不能把任务移到已完成列表，也不改变任务业务数据。
5. 本地保存失败时明确提示，界面不把未保存的顺序伪装为持久结果。
6. 短按朗读、打卡与普通滚动正常；静止长按只显示可移动反馈，不自行换位或启动边缘滚动。拖动取消不保存。
7. 反复交换第 1、2 条，再交换第 2、3 条并继续拖动时，被拖卡片始终跟手；仅本轮需要让位的邻卡移动，第 3 条不会错误占据第 2 条槽位。邻卡在松手前到达目标位置，松手后画面与保存顺序一致，无闪回、重叠或上一轮动画残留。

## 人工测试中的补充与缺陷结论

- 补充需求：用户要求移除占宽的独立拖动把手，改为整张待完成卡片长按拖动，并让孩子能明显看到“卡片已拿起、可以移动”的动画。短按任务操作和已完成列表规则保持有效。用户批准补充设计后实施。
- 缺陷第一轮：长按直接闪退；Pad 崩溃堆栈证实条件式 Compose `rememberInfiniteTransition` 造成记忆槽位类型转换异常。
- 缺陷第二至四轮：相邻卡片偶发不换位或闪回；换位后静止长按卡片自行跳位；连续交换后邻卡动画不到位。这些问题促成第五轮整体重构。
- 缺陷第五轮：反复交换后第三条错误移到第二条附近。用户明确要求重写拖动会话、几何和动画链路；最终实现以每轮实测槽位快照计算预览，手势监听固定在原槽位，基础布局在回位动画结束前不改变，提交后销毁本轮动画状态。
- 最终验收：用户于 2026-10-06 确认“没有问题了，本次所有补充需求、缺陷、需求本身全部测试完成”。
