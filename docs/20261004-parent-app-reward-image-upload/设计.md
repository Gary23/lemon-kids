# 设计：家长端奖励图片上传

## 问题分析

家长奖励编辑器目前只能设置 `cover_key`；`rewards` 表与共享 `Reward` 模型没有图片路径。孩子端奖励页的本地封面也只按 `cover_key` 选择，所以家长无法展示具体奖励物品。现有头像公开链接不适合家庭奖励照片，采用按家庭隔离的私有 Storage 对象。

## 方案目标与范围

在“我的 → 奖励管理”的新增/编辑弹窗加入单张图片选择、预览、替换和移除。图片可选，预设封面继续保留为无图或加载失败时的兜底。列表行也展示当前图片。图片修改仅更新奖励目录，不触碰价格、类型、启停或兑换历史。

## 数据与权限设计

1. 新迁移为 `public.rewards` 增加可空 `image_path TEXT`，保存 Storage 相对对象路径，不保存公开 URL 或短期签名 URL；旧记录默认 `NULL`。路径使用 `{family_uuid}/{random_uuid}.jpg`，并校验路径属于该奖励的 `family_id`。如线上现有字段/策略与设计不符，先做迁移前检查，不能直接覆盖数据。
2. 新建私有 `reward-images` bucket，限制单文件不超过 5 MB、仅 `image/jpeg`。Storage RLS 以当前 `auth.uid()` 对应的 `users.family_id` 与对象路径首段比对：本家庭已登录成员可读取，本家庭家长可新增和删除；匿名及其他家庭不可访问。为防既有宽泛 Storage 策略绕过限制，迁移还需设置适用于该 bucket 的限制性策略并实测。
3. 共享 `Reward` 增加可空 `imagePath`；创建/更新 DTO 显式写入。共享仓库提供上传、删除对象与短期签名读取接口，调用前校验路径和家庭；最终权限由数据库与 Storage RLS 执行。签名 URL 仅供页面临时显示，不写回数据库。
4. 家长使用系统图片选择器选单张图；本地校验可解码的静态图片，转为 JPEG，限制输出边长和文件大小，再上传。原文件不是合法图片、处理失败或最终文件超过 5 MB 时阻止上传并说明原因。表单中先显示本地预览。
5. 新增/替换时先上传到全新路径，再保存奖励行；数据库保存失败时删除新对象并保留原引用。替换/移除成功后删除旧对象；清理失败只记录待清理对象，不回滚已成功的奖励修改，避免页面指向不存在的对象。禁止覆盖原路径，以免旧设备缓存错误图片。无图保存不产生 Storage 对象。

## 页面与交互

- `parent-app/.../feature/profile/RewardManageScreen.kt`：表单显示“选择图片”“更换图片”“移除图片”与预览；保存中禁止重复提交；列表缩略图优先显示上传图，读取失败回退预设图标并给出可重试的提示。
- `RewardManageViewModel.kt`：维护本次选择与移除意图，调用共享仓库上传和保存，失败保持表单与旧数据，成功刷新列表。关闭未保存表单不上传。
- 图片仅作用于奖励封面；现有预设封面选择仍可设置兜底图。

## 涉及文件、依赖与顺序

- `parent-app/feature/profile/RewardManageScreen.kt`、`RewardManageViewModel.kt`：选择、预览和保存反馈。
- `shared/model/Reward.kt`、`shared/repository/RewardRepository.kt`、`shared/repository/impl/SupabaseRewardRepository.kt`：图片路径与 Storage 接口。
- 新增 `supabase/sql/20261004_reward_images.sql`：字段、私有 bucket 和策略。先在测试 Supabase 环境验证，再部署至目标环境；家长端安装之前迁移必须可用。
- [孩子端独立设计](../20261004-kid-task-app-reward-image-display/设计.md)消费上述字段和签名读取能力；此流程不修改孩子端界面。

## 风险、兼容与回滚

- Storage 上传和 PostgREST 更新不能处于同一事务。保存失败即时清理新对象；旧对象清理失败需留下日志并可按引用关系做后续清理。任何失败不得将旧奖励引用改为失效路径。
- 私有签名 URL 过期或网络失败时保留文字及预设封面；再次打开或刷新时重新签名。旧客户端忽略可空字段，旧奖励无需数据回填。
- 若回滚客户端，保留 `image_path` 和图片对象以供新版本恢复；需要回滚迁移时先停用图片入口并确认引用，再处理对象和列，不能直接删除用户照片。

## 人工测试缺陷修复设计与确认

首次安装后的相册选图失败发生在本地尺寸探测：`BitmapFactory.decodeStream` 在 `inJustDecodeBounds = true` 时正常返回空 Bitmap，但尺寸写入 `Options.outWidth/outHeight`。原实现误以空 Bitmap 为读取失败。修复将输入流是否能打开与尺寸是否有效分别判断；仅打开流失败时提示无法读取，尺寸仍由宽高校验，完整解码仍检查 Bitmap。JPEG/PNG、1600 像素最长边、5 MB 和上传流程不变。该局部修复方案已于 2026-10-04 获用户回复“批准”。

## 验收标准

1. 新建、编辑、替换、移除奖励图片后，家长列表及再次打开编辑器展示正确；不设置图片时仍按 `cover_key` 显示。
2. 非图片、超大图片、断网、上传成功但保存失败等路径均有明确结果，旧图片不丢失，数据库不出现无效引用。
3. 本家庭家长有写权限，本家庭孩子只有读权限；其他家庭和匿名无法读取或写入对象。核验旧版宽泛策略不能绕过新限制。
4. 价格、类型、启停和兑换结果不因图片变化；既有奖励无需修改即可读取。
5. 自动测试与迁移权限验证通过后，请求家长端设备安装确认；人工测试通过后再核对项目文档、提交和推送。

## 待用户确认的设计决策

- 单个奖励仅一张静态图片；上传图优先，预设封面用于无图和加载失败。
- 图片按家庭私有存储；家长可写，家庭孩子可读；采用 5 MB 上限并转为 JPEG。
- 本流程完成家长端及共享数据前置，孩子端展示另走独立流程。
