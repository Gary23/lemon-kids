# 设计：柠檬任务奖励图片展示

## 问题分析

`RewardScreen.kt` 的 `RewardCover` 与 `SmallWishCard` 只根据 `cover_key` 选择 `reward_*.jpg` 或礼物占位图。奖励快照已从本家庭读取启用目录，但模型没有上传图片路径，页面也没有访问私有图片的入口。

## 方案目标与范围

沿用当前星星银行、大心愿、小心愿和兑换记录布局。对有 `image_path` 的启用奖励，卡片封面优先加载家长图片；无图、签名失败或图片解码失败时保留现有 `cover_key` 封面。记录列表维持当前文字与操作布局，不增加历史图片快照。

## 数据与交互流程

1. 依赖[家长端设计](../20261004-parent-app-reward-image-upload/设计.md)提供 `Reward.imagePath`、`rewards.image_path`、私有 `reward-images` bucket 和共享仓库短期签名接口。孩子端不能写 Storage；服务端 RLS 校验本家庭身份。
2. `RewardViewModel` 获取本家庭启用奖励快照后，只为有路径的奖励按需生成短期签名 URL，并在页面状态中按奖励 ID 保存。签名 URL 不进入持久化模型，不写日志或数据库。图片签名失败只影响该卡片，不将整个奖励快照视为加载失败。
3. `RewardScreen.kt` 将大心愿和小心愿封面统一为“已签名上传图优先、预设图兜底”的渲染逻辑。使用 Coil 异步加载，维持现有裁切、尺寸、圆角和状态角标；加载中仍显示预设图，失败时回退。标题、积分、进度、兑换按钮始终来自原快照。
4. 首次进入和点击“刷新奖励”时重读目录并重新签名；家长替换图片时的新对象路径使缓存键变化，刷新即可看到新图。页面长时间停留而签名过期时，重新进入或刷新后恢复；必要时可对图片失败提供局部重试。

## 涉及文件、依赖与顺序

- `kid-task-app/feature/reward/RewardViewModel.kt`：签名 URL 的临时状态、失败隔离与刷新。
- `kid-task-app/feature/reward/RewardScreen.kt`：大/小心愿封面显示上传图及回退逻辑。
- 共享模型/仓库及 Supabase 迁移归家长端流程；任务端只调用已批准、已验证的读取接口。家长端数据/权限先就绪，再安装任务端版本。

## 风险、兼容与回滚

- 私有签名 URL 会过期，不能持久化；刷新时重新签名。图片加载失败不得变成空白卡片或阻断兑换。
- 旧奖励 `image_path = NULL`，直接沿用既有预设封面；旧版本任务端忽略新字段。回滚任务端只需恢复旧卡片渲染，服务端图片与家长配置保留。
- Storage RLS 若配置错误，签名会失败；自动测试与人工测试须覆盖同家庭孩子可读、跨家庭不可读。

## 验收标准

1. 家长上传图片的启用奖励在大心愿或小心愿卡片显示正确；替换/移除后刷新表现正确。
2. 无图、签名失败、下载失败均显示对应预设封面，名称、价格、积分和兑换不受影响。
3. 孩子端没有上传入口，跨家庭图片不可读取；停用奖励仍按现有目录规则不显示。
4. 自动测试通过后请求任务端设备安装确认；人工测试通过后核对项目文档、提交和推送。

## 预计同步的项目文档

人工验收后核对 `kid-task-app/README.md` 的奖励页图片展示与回退规则、`shared/README.md` 的奖励图片读取边界、`supabase/README.md` 的家长端前置迁移。最终行为若有补充或缺陷，以验收后的结论更新，执行文档逐项记录对应位置。

## 待用户确认的设计决策

- 上传图只显示在大心愿和小心愿卡片封面；兑换历史记录继续显示文字。
- 家长设置/替换后，孩子进入或手动刷新奖励页可看到最新图片；图片失败回退现有封面。
- 本需求依赖家长端流程先完成共享字段、私有存储和上传能力。
