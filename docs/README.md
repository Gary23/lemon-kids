# 需求开发流程

本目录保存每一次开发需求的过程文档，是代码实现、测试和交付的唯一过程记录。既有的历史文档可保留原位置；新需求从本规范开始执行。

## 范围与目录

一次流程只处理一个应用或独立模块。需求影响多个应用时，必须拆成多个流程并依次推进，不能共用设计确认、待办或测试结论。跨模块的模型、数据库、云函数等改动，要在各受影响流程中记录调用链和依赖关系。

新需求的目录格式如下：

```text
docs/YYYYMMDD-应用名称-需求简述/
```

日期使用需求开始当天的 `YYYYMMDD`；应用名称使用仓库目录名，例如 `parent-app`、`kid-task-app`、`kid-monitor-app`、`kid-literacy-app`、`family-video-app`、`ui-app`、`shared`、`supabase` 或 `evaluate-reading`；需求简述使用简短、小写、连字符分隔的英文或拼音标识。示例：`docs/20260920-parent-app-task-reminder/`。

每个目录的主文档固定为：

```text
需求.md
状态.md
设计.md
执行.md
```

文档不得用代码完成情况替代验收结论；需求原文、设计决策、测试命令及人工测试结果均须可追溯。

## 状态机与门禁

`状态.md` 的当前阶段只能是 `设计`、`执行`、`测试`、`完成` 之一，并记录更新时间、当前阻塞/等待项及阶段历史。

```text
收到需求
  → 创建「需求.md」「状态.md」，当前阶段：设计
  → 创建「设计.md」，继续保持：设计
  → 等待用户明确批准设计（停止）
  → 创建「执行.md」，当前阶段：执行
  → 按待办修改代码并实时勾选执行项，保持：执行
  → 待办全部完成，当前阶段：测试
  → 执行自动测试并记录结果（停止，询问是否安装到设备）
  → 用户确认安装后安装到指定设备（停止，等待人工测试）
  → 用户确认人工测试通过
  → 最小化更新应用相关文档、提交并推送远程，当前阶段：完成
```

自动测试通过不等于完成。处于 `测试` 阶段时，必须在安装前取得用户明确许可，并在安装后等待用户的人工测试结论；在此之前不得推送代码或填写完成状态。若项目或目标设备不支持安装，须在测试文档中说明替代交付验证方式，仍须等待用户的人工测试/验收确认。

## 各文档最低内容

### `需求.md`

- 需求编号/目录、日期、应用范围、提出人和原始需求描述。
- 背景、目标、非目标、约束、依赖和可验证的验收标准。
- 跨模块影响及本流程不处理的应用范围。

### `状态.md`

```markdown
# 状态

- 当前阶段：设计
- 当前步骤：等待设计确认
- 更新时间：YYYY-MM-DD HH:mm（Asia/Shanghai）
- 阻塞或等待：用户批准设计文档

## 阶段历史

| 时间 | 阶段 | 事件 | 结论/链接 |
| --- | --- | --- | --- |
| YYYY-MM-DD HH:mm | 设计 | 已创建需求与状态文档 | [需求](需求.md) |
```

### `设计.md`

- 问题分析、方案目标、范围和非目标。
- 涉及文件/模块、数据与交互流程、接口或兼容性影响、风险与回滚方案。
- 明确的验收标准和待用户确认的设计决策。
- 文末保留“设计确认”项；未取得明确批准前不得创建执行待办或改动代码。

### `执行.md`

- 与设计对应的可勾选待办，包括实现、文档、自动测试、安装和人工测试步骤。
- 每项记录结果或关联的文件/命令；代码变动后立即更新勾选状态。
- 自动测试记录：实际执行命令、结果、失败项及处理结论。

## 测试中的补充需求与缺陷

在等待人工测试期间，如果用户提出新的内容：

- 明确是新增能力、范围扩大或体验调整时，视为补充需求。
- 明确是未满足本次验收标准、报错、崩溃、数据错误或行为不符合设计时，视为缺陷。
- 描述无法明确归类时，必须先询问用户是“补充需求”还是“缺陷”，不可自行假定。

补充需求从头创建 `补充-需求.md`、`补充-状态.md`、`补充-设计.md`、`补充-执行.md`，并完整重复上述状态机；缺陷同理创建 `缺陷-需求.md`、`缺陷-状态.md`、`缺陷-设计.md`、`缺陷-执行.md`，从设计阶段重新开始。两种情况都必须再次等待设计批准、自动测试、安装确认和人工测试确认。

补充/缺陷经人工测试通过后，将其需求、设计、执行和测试结论合并回主文档的对应章节；确认主文档已完整包含相关内容后，直接删除对应的带前缀文档。随后再按实际改动最小化更新对应应用的 README、架构/产品说明或部署说明，最后提交并推送远程，并把主 `状态.md` 更新为 `完成`。

## 完成前检查

- [ ] 当前流程仅包含一个应用/模块；多应用需求已拆分。
- [ ] 需求、状态、设计和执行文档齐全，状态历史完整。
- [ ] 设计已得到用户明确批准后才改动代码。
- [ ] 执行待办、自动测试命令和结果已如实更新。
- [ ] 已获得安装许可，且人工测试结论已由用户明确确认。
- [ ] 已最小化更新受影响应用的相关文档。
- [ ] 代码已提交并推送，`状态.md` 已改为 `完成`。
