# 设计：家长端奖励图片接受静态 WebP

## 问题分析

`RewardImageProcessor.kt` 在解码前只接受 `image/jpeg` 和 `image/png`，WebP 被 MIME 校验直接拒绝。后续流程已经把可解码输入压缩成 JPEG；`SupabaseRewardRepository` 校验 JPEG 文件头并生成 `.jpg` 路径，Storage bucket 仅允许 `image/jpeg`。孩子端 `RewardScreen.kt` 用 Coil 加载签名 URL，不按原始输入格式分支。

## 方案目标与范围

家长端接受静态 `image/webp`，经过现有解码、缩放与 JPEG 压缩链路后预览和上传。奖励仍只保存一张静态封面，动画播放不在本方案范围。JPEG/PNG 输入保持可用，存储格式、共享接口和孩子端代码不变。

## 数据与交互流程

1. 系统图片选择器仍使用 `image/*`；`prepareRewardImage` 的输入 MIME 白名单加入 `image/webp`，并更新格式错误提示。输入仍须通过有效宽高和完整解码校验。
2. WebP 图像按现有逻辑处理方向、最长边限制和 JPEG 质量参数；处理后的 JPEG 字节用于本地预览、共享仓库上传和保存。输出超过 5 MB、损坏或无法读取时沿用明确错误提示，不更新奖励引用。
3. `RewardManageViewModel` 的保存和清理顺序不变；列表、编辑页继续加载 `.jpg` 签名 URL。孩子端也继续加载同一 `.jpg`，无需增加 WebP 解码或路径分支。
4. 动画 WebP 若被系统选中，仅能作为静态封面处理；不承诺保存动画。人工测试应使用静态 WebP 样本。

## 涉及文件与兼容性

- `parent-app/.../feature/profile/RewardImageProcessor.kt`：输入格式校验和提示。
- `parent-app/README.md`：人工验收后更新可选格式与仍转 JPEG 的长期规则。
- `shared/README.md`、`supabase/README.md`、`kid-task-app/README.md`：验收后核对现有 JPEG 存储和孩子端读取描述；若现有内容已准确，不重复修改。
- 不改 `shared`、`supabase/sql` 或 `kid-task-app` 的业务代码。已有 `.jpg` 路径、bucket MIME 规则及孩子端签名读取保持兼容。

## 自动测试与人工验收

- 自动测试验证 WebP 输入能通过处理并生成 JPEG，以及损坏图片会失败；同时运行家长端相关测试与构建。若单元测试环境无法真实解码 Android WebP，则以可运行的构建和设备人工选图补足，并在执行文档如实记录限制。
- 安装确认后，在设备上用静态 WebP 完成新增、预览、保存、替换、移除；在柠檬任务 App 刷新奖励页核对显示，无需安装新的孩子端包。
- JPEG/PNG 与无图奖励做回归核对；WebP 输出超过上限或无法解码时确认没有失效引用。

## 风险与回滚

- 部分图片提供方可能返回错误 MIME，现有机制会拒绝并显示格式提示；本次按提供方报告的 `image/webp` 接受，不根据扩展名放宽校验。
- 转 JPEG 会丢失 WebP 的透明通道和动画信息，视觉上沿用当前 JPEG 封面规则。若要求保留透明或动画，需另行设计存储与显示行为。
- 回滚家长端输入白名单即可恢复原选择规则；既有上传对象仍是 JPEG，无需迁移或清理。

## 待用户确认的设计决策

- “支持 WebP”定义为支持选取静态 WebP 输入，上传前仍转成 JPEG；奖励不保留 WebP 原文件或动画。
- 在该方案下柠檬任务 App 不需要代码改动，人工验收时使用当前 App 刷新奖励页验证展示。
