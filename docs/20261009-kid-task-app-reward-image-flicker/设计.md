# 设计：奖励图片刷新期间保持稳定

## 问题分析

`RewardViewModel.refresh()` 成功读取奖励快照后立即把 `imageUrls` 清空，随后调用 `resolveRewardImageUrls()` 重新签名；`submit()` 重新读取快照时也会清空地址。签名需要网络时间，其间 `RewardImage` 收到空地址，显示预设封面。新地址返回后，`AsyncImage` 的 `onLoading` 又把 `imageLoaded` 设为 `false`，在下载或缓存命中前继续显示预设封面。这与“家长图→默认图→约一秒后家长图”的现象吻合。滚动本身是否触发了页面恢复或另一轮刷新，仍需设备日志/人工复测确认。

## 目标与范围

让同一家庭、同一奖励、同一 `image_path` 的已加载封面在刷新中保持稳定；对图片被替换、移除、切换家庭或真实加载失败的情况维持现有兜底语义。只改孩子端奖励页状态与渲染，不改变签名接口、存储策略、兑换数据。

## 方案

1. `RewardViewModel.kt` 在快照更新时，以家庭 ID、奖励 ID 和 `image_path` 判定已有图片地址能否继续显示。相同来源在新签名完成前保留；路径消失、路径变化或家庭切换时立即丢弃旧地址，防止旧图片错配。
2. 对同一来源避免每次刷新都替换可用的签名 URL。记录短期地址的生成时间，在其 10 分钟有效期接近结束时再签名；到期或需要重签时，在新地址可用且图片成功加载前保留当前已显示图片。签名失败时保持可用的旧图直至到期，过期后回退预设封面。缓存只存在内存中，不写日志或持久化。
3. `RewardScreen.kt` 的 `RewardImage` 在同一来源的图片请求重新加载时保留已成功显示的画面；新请求成功后替换。首次加载、真实失败、配置移除时继续显示预设封面。图片请求状态与奖励 ID/路径绑定，避免滚动重组把旧图用于别的卡片。
4. 保留首次进入和手动刷新对奖励目录的读取能力；签名失败仍按单卡处理，不阻断整个页面或兑换。

## 涉及文件与交互流程

- `kid-task-app/src/main/java/com/lemonkids/kidtask/feature/reward/RewardViewModel.kt`：保留匹配的图片地址、签名时效与更新规则。
- `kid-task-app/src/main/java/com/lemonkids/kidtask/feature/reward/RewardScreen.kt`：封面请求切换期间的显示状态。
- `kid-task-app/src/test/java/com/lemonkids/kidtask/feature/reward/RewardImageUrlsTest.kt` 或同目录相关测试：验证同路径刷新、换路径、移除和家庭切换时的地址选择；按项目自动测试门禁运行。
- `kid-task-app/README.md`：人工验收后核对奖励页刷新及失败回退的长期说明。

## 兼容、风险与回滚

- 图片 URL 是有时效的私有签名地址。旧地址超时后不能无限保留；新签名失败时最终须回退预设封面。
- 快速连续刷新与较慢的签名请求可能交错，结果只应用于仍匹配的快照和家庭；旧请求不得覆盖新配置。
- 若设备上仍可复现，记录触发时的页面生命周期和图片请求日志，调整刷新入口或图片状态管理。回滚可恢复原孩子端 ViewModel 与封面组件，不涉及数据迁移。

## 验收标准

按[需求](需求.md)的四项标准执行。人工测试应在实际配置图片的大/小心愿上连续滚动、离开再返回、手动刷新，并覆盖家长端替换与移除图片。

## 待用户确认的设计决策

- 相同图片来源刷新时保持当前封面，签名临近过期时更新；配置变化时立即舍弃旧图片。
- 图片请求真实失败或到期无法重新签名时使用预设封面。
