# 需求：家长端成长勋章进度

- 需求编号：20261005-parent-app-task-growth-domain
- 日期：2026-10-05
- 应用范围：`parent-app`
- 提出人：用户

## 最终验收范围

原任务领域方案曾实现并安装，人工测试期间用户改为家长手动维护勋章进度，并要求移除原入口、保留历史数据。用户于 2026-10-05 明确要求将本单的补充和缺陷标记为完成，作为家长端最终人工验收结论。现行功能是“我的 → 勋章进度”：按孩子分别录入 13 条专项累计数量，英语阅读 A～Z 逐级录入；可增可减，保存后以服务端记录为准。专项与任务库和任务完成脱钩；两条习惯勋章仍按任务统计。旧任务领域字段、值及 RPC 留存兼容，界面入口已移除。

最终验收还包括两项缺陷结论：旧领域菜单的字号统一修复已安装，随后该入口按补充需求移除；认字进度首次 1071 字已写入却报错的情况已修复，保存后重新核对服务端值，真实版本冲突提示最新值且保留输入，界面不展示请求头。勋章数据由 Supabase 受控 RPC、RLS 与审计保障；孩子端展示属于独立流程。

## 原始需求

> 关于勋章，你思考一下，如何跟阅读任务、计算任务、默写任务、英语任务等等做对应关系，能否完成对应任务就积累对应的勋章级别

> 关于勋章，你设计一下一般小学生都需要哪些勋章，给我设计一个体系名称，勋章在不同等级阶段应该也有不同名称

> 阅读、计算、任务、打卡、劳动与自理，这些是频率最高的，一个月按道理应该是有20-25次的；默写、英语、写作表达、科学探索（改为数学思维）每月约10-15次；运动、艺术创作不需要，只保留学习相关的勋章。

## 原始背景与目标（历史方案，现行规则见上）

家长端的任务库模板目前只有标题、描述和积分；分类由家庭自定义，同一模板可以归多个分类，不能可靠代表阅读、计算等学科。家长在任务库明确标注一个主要成长领域，日程创建时将该领域保存为任务实例快照，供孩子端真实勋章计算使用。

## 范围

- 在家长端任务库创建/编辑时从七个成长领域（阅读、计算、默写、英语、写作表达、数学思维、劳动与自理）或“综合/不计专项”中选择一个主要领域。
- 新建任务实例继承任务模板的领域快照；编辑模板不悄悄改变既有任务的成长领域。
- 家长可预览并明确确认一次性为同模板、尚未标注领域的历史任务补标，以便已有真实完成记录参与对应勋章。

## 非目标与跨应用边界

- 本流程不改孩子端勋章页面、等级或成长文案；它们由独立的 `kid-task-app` 流程设计、确认和验收。
- 不按任务标题、家庭自定义分类名称或 AI 自动猜测领域；不评价阅读理解、计算正确率或默写准确率。
- 不改变现有任务完成、撤销、积分规则。

## 验收标准

1. 家长可看见并编辑模板的主要成长领域；新模板默认“综合/不计专项”，旧模板显示“未设置”，不会自动判为任何学科。
2. 新任务实例获得正确的领域快照；同一模板即使放在不同自定义分类中，领域仍一致。
3. 更改模板领域不修改既有实例；历史补标展示影响数量并由家长明确确认，且只改未标注的本人家庭任务。
4. 任务历史及积分保持不变；旧客户端仍可正常创建任务，缺失领域视为未标注。
5. 设计确认、自动测试、设备安装确认、人工测试和文档同步遵循 `docs/README.md`。

## 依赖

本流程包含 `:shared` 的任务模板/任务模型与仓库写入字段，以及 Supabase 模板字段、任务实例快照、任务创建 RPC、受控历史补标 RPC。孩子端 `kid-task-app` 成长快照流程依赖这些已验收的数据能力，两个应用分别确认和验收。
