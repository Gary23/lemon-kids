# 需求

- 需求编号：20260930-kid-task-app-real-rewards
- 日期：2026-09-30
- 应用范围：`kid-task-app`（依赖 `shared` 奖励模型/仓库及 Supabase 兑换事务）
- 提出人：用户

## 原始需求与补充

> 柠檬任务app，分析一下我要建立奖励系统，页面现在已经有了，需要在家长端设置奖励，在柠檬任务重查看和兑换奖励，先分析设计一下

> 奖励要分一次性奖励和常规奖励，其中常规奖励可兑换多次，还需要孩子能看到自己已经兑换的奖励，使用后由任务端去执行删除操作，已经兑换的奖励也可以在任务端进行取消归还星星，家长端基本只负责待兑换奖励的维护

用户已确认：孩子兑换时直接扣积分；同一家庭的孩子共用奖励清单；一次性奖励全家总共可兑换一次，未使用前取消后恢复名额。

## 背景与目标

孩子端已有“奖励兑换”页面和真实积分余额，但心愿卡片、月累计、兑换记录及申请弹窗是明确标注的本地演示。接入家长配置的真实奖励，并由孩子端管理自己已经兑换、尚未使用的奖励。

## 范围

- 展示本家庭启用奖励、大心愿、真实积分余额与真实兑换记录。
- 积分足够时二次确认兑换；服务端成功后更新余额和记录，失败不显示成功。
- “兑换与奖励记录”以单列表展示本人待使用、已使用和可辨识的旧版兑换；待使用奖励可标记“使用”或“取消兑换”并退回原价星星，取消记录只保留在服务端审计中。
- 一次性奖励兑出后不可再兑，取消后重新可兑；常规奖励可多次兑换，每次形成独立记录。
- 数据为空、加载失败、余额未知、积分不足及一次性奖励已兑均有明确状态。

## 非目标

- 不在本流程改动家长端奖励设置；见[家长端需求](../20260930-parent-app-reward-management/需求.md)。
- 不实现孩子自行创建心愿、成长等级或勋章；不做家长预先审批和图片上传。
- 不提供家长端兑现确认、系统推送或永久删除积分审计记录。

## 约束与依赖

- 保留 2026-09-30 已验收的星星银行、大心愿、小心愿、记录等主要视觉结构；移除已经失效的演示数值与演示成功文案。
- 奖励目录字段与家长端管理由家长端流程先提供；本流程建立孩子自己的兑换记录、原子兑换/取消事务和使用标记，记录共享层、数据库与家长端目录的依赖。
- 真实扣分和退款只能走数据库事务，UI 不直接修改积分；用户已确认“使用后删除”是移出未使用列表并保留历史，且使用后不可取消退星。
- 本流程单独经过设计批准、自动测试、安装许可和人工测试确认。

## 验收标准

1. 家长新增/停用奖励后，孩子进入或刷新页面可看到对应变化；其他家庭奖励不可见。
2. 余额未知时不可兑换；积分不足时按钮不可用并显示差额；足够时确认后仅成功扣一次，侧栏、银行余额和记录一致。
3. 常规奖励可重复兑换且每次独立出现在记录列表；一次性奖励成功后不可再兑，取消后恢复可兑（家长仍启用时）。
4. 取消未使用奖励恰好退回兑换时扣除的星星并从页面记录列表消失；使用后留在同一列表且显示“已使用”。兑换、取消、使用及积分变化都有可追溯记录。
5. 网络或服务端失败不改变显示余额或兑换状态，并允许安全重试。

## 已验收缺陷：统计标量解码

2026-09-30 用户在部署孩子端迁移后反馈奖励页仍提示网络不通。线上接口均可达，根因是客户端将 `get_monthly_task_points` 的 JSON 整数标量按列表解码。缺陷验收要求页面正确读取真实奖励、余额和本月收益；失败时记录可定位的异常并允许重试。用户在修复版安装 Pad 后明确反馈“本次缺陷修复完成”。

## 已验收补充：奖励页视觉与记录布局

用户要求依照 Stitch MCP 中的奖励屏幕修正大心愿、小心愿和兑换记录三个区域。Pad 人工测试又明确了最终布局：页面顶部直接显示星星银行，刷新按钮置于银行内；横屏小心愿三列，移除冗余兑换类型文字，兑换按钮采用深绿背景与白字；记录只有一个列表，标题和星星数同排、状态和日期在左侧第二排，右侧仅放“使用”“取消兑换”按钮。取消记录不在页面展示，旧版有效兑换仍可辨识。数值和记录均来自真实数据，不使用 Stitch 静态示例。用户于 2026-10-01 确认本次需求完成。

## 已验收缺陷：刷新按钮与记录细节

刷新奖励使用深绿实体按钮；大心愿不显示“全家限兑一次”或“可重复兑换”辅助行；兑换记录日期紧跟左侧状态。刷新按钮进入“刷新中…”禁用态时仍保持白字与深绿背景，继续禁止重复点击。两轮修正版均通过自动测试并在用户确认后安装到 Pad；用户于 2026-10-01 明确要求“本轮缺陷全部改为已完成”。
