# 设计：柠檬任务兑换、持有与退星

## 问题分析

`RewardScreen.kt` 保留已验收的星星银行布局，但 `RewardDemoUiState` 中五个心愿、两条记录、大心愿进度和本月 186 星全是静态示例；点击按钮只在本页显示“未通知家长、未扣星”。真实积分来自 `HomeViewModel`，但共享仓库当前五分钟轮询，兑换后侧栏可能长时间显示旧余额。现有 `redeem_reward` 缺少归属和幂等校验，也无法表达孩子已经兑换、使用及取消退星。

## 目标与范围

保留“银行 → 大心愿 → 小心愿 → 兑换与奖励记录 → 页尾”主要层级，记录区使用一个列表。用本家庭奖励及真实积分、兑换记录替换演示内容。家长可选一个启用奖励作为大心愿，其余启用奖励以横屏三列卡片显示；没有大心愿时省略该卡，所有奖励显示在网格。支持窄屏减列和纵向滚动。当前不接入等级、勋章或孩子投递心愿。

## 兑换状态与业务规则

| 状态 | 孩子端位置 | 允许操作 | 积分结果 |
| --- | --- | --- | --- |
| `held`（已兑换、未使用） | 统一记录列表 | 使用；取消兑换 | 兑换时已扣积分 |
| `used`（已使用） | 统一记录列表 | 无 | 不退积分 |
| `cancelled`（已取消） | 页面不展示，服务端保留审计 | 无 | 按兑换时价格退积分一次 |

“使用后删除”最终解释为从待使用状态移出，服务端记录变为 `used` 并留在同一记录列表，不物理删除兑换、积分流水或历史。用户已确认只有使用前可取消；两个操作都要二次确认。一条常规奖励可重复兑换，每次生成独立的持有记录并分别使用/取消。一次性奖励按家庭只允许存在一条未取消记录；取消后恢复可兑（家长仍启用时），已使用则永久占用。

## 数据与交互流程

1. 页面从当前孩子身份取得 `family_id`、孩子 ID、启用奖励、余额、当前月任务赚取积分和自己的兑换记录。首次读取前显示加载状态，失败时保留重试入口；不能把未知余额当 0。孩子只看到自己的持有与历史，即使奖励目录为家庭共用。
2. 奖励卡显示家长设置的名称、说明、预设封面/图标、价格、可重复规则。大心愿进度按 `min(当前真实余额 / 价格, 100%)` 显示，差额用真实余额计算；不得继续显示演示的 133/200、66%。本月赚取从该孩子本月真实 `task_complete` 积分流水汇总，不能用仓库最多 50 条记录截断计算。
3. 余额足够且奖励启用、一次性奖励尚未被占用时点击“兑换”，展示奖励名称、扣减星数和预计余额；确认时生成一次请求 ID，提交期间禁用按钮。请求结果未确认时保留该 ID，超时重试复用同一 ID；服务端对账前不生成新的兑换请求。
4. `redeem_reward` 在一个事务中验证当前孩子、家庭、奖励启用、类型、余额和请求 ID；锁定奖励和孩子余额；扣积分、写 `point_records` 与一条 `held` 兑换记录。重复请求同一 ID 且参数一致返回既有结果，参数不同拒绝。**不修改**奖励的 `is_active`，避免取消后错误重开家长停用的奖励。
5. `cancel_reward_redemption` 仅接受兑换本人名下的 `held` 记录，锁定该记录与余额，按记录内的**兑换时价格快照**加回星星，写一条 `reward_refund` 积分流水并改为 `cancelled`。重复取消不二次退款；`used` 拒绝取消。取消一次性奖励后，服务端重新计算其可兑状态。
6. `use_reward_redemption` 仅接受兑换本人名下的 `held` 记录，原子改为 `used` 并记录使用时间；重复提交安全返回，`cancelled` 不可使用。标记使用不改变积分或家长目录启停。
7. 兑换、取消或标记使用成功后主动刷新余额、奖励目录、持有和历史，并通知 `HomeViewModel` 刷新侧栏积分。失败按余额不足、已取消/已使用、奖励停用、连接失败等给出明确反馈并重读服务端事实；不得先在本地展示扣分/退款成功。

## 数据模型与权限

- 新增 `reward_redemptions`：请求 ID/主键、家庭、孩子、奖励 ID、兑换时名称/价格/类型快照、`held`/`used`/`cancelled` 状态、兑换/使用/取消时间及关联积分流水 ID。历史数据不得因家长之后改名、改价或停用而改变。
- 扩展 `point_records` 的类型与关联字段，支持 `reward_refund` 并将退款准确关联到原兑换；兑换记录与积分流水只追加或改状态，不因“删除”物理清除。
- 数据库只允许孩子读取自己的兑换明细；家长端本期不读取兑换记录，也没有使用/取消/退款权限。扣分、退款和使用状态只能通过鉴权 RPC 改动。一次性奖励并发兑换必须在锁定奖励行后判断是否已有未取消兑换；已有兑换历史的奖励类型不可修改。
- 若线上已有旧 `reward_redeem` 流水而无对应兑换 ID，保留为“旧版历史兑换，状态未知”；不能自动开放取消退星，以免重复退款，也不能伪装成当前持有奖励。

## 涉及文件/模块

- `kid-task-app/feature/reward/RewardScreen.kt`、`RewardViewModel.kt`：移除示例心愿与申请逻辑，接入真实加载、兑换确认、单列表记录、使用与取消确认及结果状态；保留已验收的视觉结构。
- `kid-task-app/navigation/KidTaskNavGraph.kt`、`feature/home/HomeViewModel.kt`：兑换后同步银行、侧栏及成长页所共用的积分状态。
- `shared/model/Reward.kt`、新的兑换记录模型、`PointRecord.kt`、`RewardRepository.kt`、`SupabaseRewardRepository.kt`：消费家长端目录字段，增加持有/历史读取与安全兑换、取消、使用接口；页面打开/恢复及操作后主动刷新，不依赖五分钟轮询。
- Supabase 迁移：本流程新增兑换表、权限、`reward_refund` 流水类型与三种孩子端 RPC，并替换旧 `redeem_reward`；依赖[家长端设计](../20260930-parent-app-reward-management/设计.md)先完成目录迁移。

## 兼容性、风险与回滚

- 家长端目录迁移先到位，再部署孩子端事务并启用真实兑换。旧版本孩子端仍只做演示；新版本若后端未准备好须显示不可用，不能以本地成功替代。
- 余额不足、两个设备同时兑换、网络超时重试、重复点击、取消与使用并发，以及家长中途停用，均以事务结果为准。请求 ID 保证同一兑换意图不会重复扣分。
- 一次性奖励按家庭范围消耗；已使用后不可因家长重新启用而重新兑换。若用户选择按孩子限制，需同步修改家长端与 SQL 设计。
- 已花出的任务积分若不足以完整退回，任务撤销被服务端拒绝并给出清晰提示；不能因撤销把账户余额截断为零而破坏积分流水。
- 回滚 UI 时保留真实积分流水及兑换记录，不删除历史。旧 `redeem_reward` 的不安全定义必须被事务迁移替换，且 RPC 权限收紧。

## 验收标准

1. 家庭内启用奖励与大心愿按家长配置展示；无数据及错误状态准确。
2. 大心愿进度、月赚取、可用余额、差额均来自真实数据，并与侧栏一致。
3. 常规奖励可兑换多次，每次独立持有；一次性奖励家庭限兑一次，取消后恢复可兑，已使用后不可再兑。
4. 成功兑换恰好扣一次分；仅持有状态可取消并按原价恰好退一次；使用后从持有列表移出且不能退款，历史保留。
5. 两个设备并发、双击、重试、跨家庭和无权限调用均不能制造额外扣分、退款或状态错乱。
6. 自动测试通过后再请求设备安装确认，安装后等待孩子端人工测试结论。

## 已确认的业务规则与设计确认项

已确认：兑换时直接扣分，奖励目录家庭共用；常规奖励可重复兑换；孩子可查看自己的已兑换奖励；使用后移出持有列表但保留历史；只有使用前可取消退星；家长只维护待兑换目录。一次性奖励**全家总共可兑换一次**，取消未使用的兑换后释放名额，已使用则永久占用。

已批准的设计决策：积分已花出且余额不足以完整退回任务所得积分时，禁止撤销对应任务，避免积分余额与流水不一致。

## 设计确认

- 状态：用户于 2026-09-30 明确批准本设计并要求开始开发；积分不足时禁止撤销任务的设计建议一并按本设计实施。

## 已批准并验收的缺陷修订：奖励页统计读取

用户执行 `supabase/sql/20260930_kid_real_rewards.sql` 后，线上 `reward_redemptions` 表和页面所需只读接口均可用。`get_monthly_task_points` 返回 JSON 整数标量，原客户端使用 `decodeSingle<Int>()` 按列表解码，导致奖励快照整体失败。用户于 2026-09-30 明确批准修复设计，随后确认修复完成。

- `SupabaseRewardRepository.getRewardSnapshot` 改用 `decodeAs<Int>()` 读取统计标量；记录失败阶段与异常堆栈，不输出会话凭据。
- `RewardViewModel` 记录奖励页读取异常，页面保留重试入口并使用中性的失败提示，不再把所有错误归因为断网或迁移失败。
- 保持 RPC 签名、余额计算、兑换事务、数据库记录和用户会话不变。真实网络或权限失败仍显示失败态，不产生假余额或假成功。
- 自动测试和 Debug 构建通过，经用户再次确认后安装到 Pad，用户确认本次缺陷修复完成。测试与安装细节见[执行](执行.md)。

## 已批准并验收的视觉补充与后续缺陷修订

以 Stitch MCP 奖励屏幕 `bd269692341947c9b0224c2268a38c27` 为视觉依据，并按 Pad 人工反馈完成两轮调整。奖励页顶部直接显示星星银行；银行内刷新入口采用圆角深绿 `#006E2F` 背景、白字和 `#005321` 底影，禁用且显示“刷新中…”时显式保持同色背景与白字，禁止重复提交。

大心愿保留宽屏图文布局、真实价格/进度/余额不足反馈和操作入口，移除“全家限兑一次/可重复兑换”辅助行，但服务端一次性限制不变。小心愿在目标 Pad 横屏按三列展示；卡片封面角标说明真实可兑状态，底部价格与深绿白字“立即兑换”同排，不显示多余的类别文案。数量、价格与说明均来自家长目录，不使用设计稿示例值。

记录区只有一个白色容器和单列表：过滤 `cancelled`，按兑换时间排序展示 `held`、`used` 及可辨识的旧版兑换流水。每行左侧第一排是标题与星星数，第二排是状态及紧跟其后的兑换日期；右侧仅待使用记录有“使用”和“取消兑换”两个有背景色的按钮。窄屏允许操作按钮另起一行，日期仍在左侧信息区。取消记录只留在服务端用于退款审计，使用后记录留在列表并显示“已使用”。保留二次确认及原价退款规则。

用户分别批准视觉补充和两轮缺陷设计，历次版本自动测试通过并在用户确认后安装至 Pad；2026-10-01 用户确认本轮缺陷及本次需求完成。具体测试、安装与人工验收记录见[执行](执行.md)。
